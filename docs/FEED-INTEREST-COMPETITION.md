# feed：概念群与兴趣竞争

本阶段让兴趣影响搜索词和最终阅读清单，沿用共享决策评分、疲劳、扰动和历史回放。没有增加后台模型，也没有接管收藏、评论、私信或证明视频已经看完。

## 启用及模式

沿用 `conceptSystem.observe` 和 `mode`。observe=false 保持原有关键词与排序，不创建概念数据库；observe=true、mode=shadow 使用原搜索词和实际清单，仅记录概念预演，不更新疲劳；mode=active 使用兴趣搜索与竞争清单，并提交实际选入清单的决策。默认仍为 observe=false、shadow；修改源码不会自动更改在线配置或重新加载插件。

`learning` 开关控制上一阶段的消息学习任务，不控制显式调用 feed。学习暂停时，active feed 仍可以读取已有概念群并记录选题疲劳。希望完全关闭概念选题时使用 observe=false（宿主观察开关的生效方式见自动学习文档），或用 shadow 保留选题预演。

## 从集合到兴趣方向

兴趣是概念群在 feed 场景下的一个视图。本版只采用 fish 主体、accepted 状态、带 topic 标签、general/feed 场景、explicit/mention 解释的成员。主人自己的兴趣、口癖和句式、否定/引用/不确定条目不会自动变成鱼的选题偏好。mention 只作为较弱的探索线索，不表示喜欢。

搜索规划按集合强度、已有奖励、feed 场景疲劳和扰动竞争，取最多四个方向，再补配置偏好/旧日记关键词，总共最多六个搜索词。集合内的不同话题再使用共享评分和近分扰动竞争一个搜索词，避免永远只搜索最早加入的成员。每个话题用短正文作为词，正文过长时用集合名；目前是字面量启发式，不做语义分词或近义词召回。短名单最多二十个，截断前已考虑有效分数和近分扰动，避免仅按原始强度或固定 ID 排序而永久排除已恢复方向及同分新成员。

搜索规划保留标准 preview，但不会提交或消耗疲劳。只有选入最终阅读清单的决策才会提交。原有搜索缓存、请求保护、热门/排行/关注来源继续使用。

## 视频竞争

先执行去重、已看/已评论、已收藏/反馈视频、自身 UP、质量下限等原有排除逻辑；配置 dislike 现在也作为标题字面量排除条件生效，兴趣竞争不能绕过。播放量继续只用于质量下限，不参与加权。

标题按话题正文、集合名和触发词匹配；成员 exclusions 命中时不采用该成员的贡献。ASCII 关键词不匹配更长英文词内部的片段，例如 AI 不匹配 chair。单个汉字话题（如“猫”）可用。这里没有根据评论或正文判断实际视频语义，也不能识别标题里的否定、讽刺或标题党；这些留给后续 debrief。

每个匹配集合提供一个成员贡献，明确话题 strength=1，提及线索 strength=0.7。旧的弹幕密度、配置偏好与反馈主题词分数 q 保留为有限的相关性修正：relevance = 0.8 + 0.2 × q/(q+8)。之后使用共享 concept-v1 评分：独立来源去重后的 `集合强度 × relevance × strength × (1−疲劳)` 均值，加上扰动。集合强度仍包含历史来源积累与已有反馈奖励；本阶段不会自动奖励获胜者。

逐个名额竞争，每次按当前有效分数（含近分有界扰动）重建最多二十条的候选短名单，使用新的名额种子。active 提交后立即增加所选集合的 feed 疲劳，再竞争下一名额，因此疲劳在同一轮内也会影响后面的选择。每个命中集合最多占 `--per` 个名额；同一 BV 不重复。不足时可补入旧清单中没有概念命中的候选；不为了凑满数量越过集合限额。没有可用鱼话题或没有标题命中时明确报告兜底，保留旧清单，不捏造概念贡献。

疲劳沿用每次 +0.2、上限 0.9、半衰期六小时。扰动沿用只对距离最佳基础分 ≤0.1 的候选施加最多 ±0.05 的带种子噪声，不让明显低分候选靠任意随机数获胜。它会改变实际输出顺序，不只是写进日志。当前没有显式的“娱乐→动漫”父子层级，先做同层兴趣和视频的两段竞争。

## 回执、重试及观察

```sh
node tools/bili.mjs feed --n 5 --per 2 --seed nightly-example --run-id nightly-example --json
```

默认每次命令生成新的 run-id 和种子；明确提供 run-id 时，默认以它作为种子。相同完整状态、输入和种子可回放；仅仅使用相同种子不能消除疲劳或学习状态变化。

夜间唤醒命令包含由持久化作息计划生成的稳定 run-id，同一计划的投递或命令重试可以恢复同一清单，不要求主人临时提醒。手工运行未指定 ID 的 feed 仍表示一轮新的选题。

同一 run-id 的完整清单、逐项决策、状态版本及疲劳更新在一个 SQLite 事务中提交。途中失败全部回滚；进程在提交后、输出前退出时，下次相同 CLI 请求直接恢复已保存清单，不依赖网络、凭据或搜索缓存，也不再次增加疲劳。run-id 对应的 n/per、种子、模式或搜索参数不一致会报错；新的意图应使用新 run-id。共享决策核心的普通 preview/commit 冲突检查仍保留；feed 在单一写事务内计算并提交，没有跨阶段的陈旧预演窗口。

`feed.search_planned` 保存实际/建议搜索词；`feed.candidates` 引用脱敏候选池及旧排序；`feed.slot_candidates` 记录每个名额的短名单和集合配额；`feed.selected` 记录最终清单、种子、范围和兜底原因。每条正式选题都产生标准 decision.previewed/committed 和 concept_state 版本，可在现有观察页查看分数、疲劳、扰动与历史回放。影子预演保持 pending，不伪装成已经采用。

清单的含义是“决定接下来读这些候选”，不是“实际看过/看完”。它不会写入已看记录、改动日记或增加正面奖励。夜间提示已要求按 feed 的顺序开始浅读；模型在后续深读阶段仍可能选择不同视频，本阶段没有把 debrief 做成强制执行门禁或观看回执。

验证使用临时数据库、模拟视频与拦截所有请求的 CLI 子进程，不访问真实 B 站或在线学习数据。
